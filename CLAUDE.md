# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A railway company simulator in static HTML + JavaScript with basic 3D graphics (three.js). Players place towns, draw Bézier-curved tracks, build stations to connect towns to the railway, then run trains that pick up and deliver passengers to earn money. The game logic is 2D (top-down, pixel coordinates); only the view is 3D.

## Running the Project

There is no build step, no npm dependencies, and no lint tool. three.js 0.160.0 is vendored at `vendor/three.module.js` and mapped by the importmap in `index.html`, so the game works offline. Serve the repo root and open it (ES modules don't load from `file://`):
```
python3 -m http.server 8000    # then http://localhost:8000
```

Run the unit tests (Node 22+) with:
```
node tests/run_tests.js
```

Pushes to `main` run the tests and publish `index.html`, `src/` and `vendor/` to GitHub Pages (`.github/workflows/deploy-pages.yml`).

## Architecture

All modules are plain ES classes in `src/`. Back-references (`Station.town`, `Platform.station`, `TrackSegment.platform`, `reverse`, `reservedBy`, `blockedBy`, crossing tracks) are ordinary object references — the garbage collector handles cycles.

```
main.js                   — DOM input → Game.handleInput, camera controls, frame loop, tip/status lines
toolbar.js                — DOM toolbar: build tools and run controls via Game's tool/command API
renderer.js               — three.js scene; reads Game state, never mutates it
orders_panel.js           — DOM side panel managing each train's cars and orders via Game's API
game.js (Game)            — game state, rules, input handling, simulation tick
├── TrackNetwork          — directed graph of junctions; Dijkstra pathfinding
│   ├── NetworkNode[]     — junction nodes (position only)
│   ├── TrackSegment[]    — Bézier curve path between two junctions (Curve2D)
│   └── TrackCrossing[]   — mutual exclusion between two tracks, no
│                           connectivity: a flat crossing (DIAMOND) or a
│                           double-track taper pair (FOUL)
├── TrackEditor           — drawing state, split/delete, station placement, double track
├── Town[]                — circle on the map; color, radius, passenger pool
│   └── Station           — links a town to the track via Platform(s)
│       └── Platform      — forward/reverse platform segment pair + side/width
├── TrainPlan[]           — edit-mode roster: per-train orders + car count
├── Train[]               — moves along a route, boards/unloads passengers,
│                           holds track reservations (one Train per TrainPlan)
└── GameSnapshot[]        — undo stack: deep copies of the editable world
```

`vec2.js` provides the immutable `Vec2` (Godot-compatible semantics: `orthogonal()` is `(y, -x)`, `angleDifference` wraps to [-π, π]) plus `Rect2` and segment intersection; `curve2d.js` is a Bézier chain baked to a ~5 px polyline (`BAKE_INTERVAL`) that all length, sampling, and closest-point queries run on.

**Tools and the toolbar** (`game.js`, `toolbar.js`): the edit sub-modes are flags — `editingOrders`, `placingStation`, `placingSignal`, `placingTown`, `placingCrossover`, `deleting`, at most one set (`_clearModes`); none set means drawing track, single or double per `TrackEditor.doubleTrack`. `Game.tool` names the active one (`'track' | 'double' | 'town' | 'station' | 'signal' | 'crossover' | 'delete' | 'orders'`, null while simulating) and `setTool(tool)` switches it (cancelling a drawing unless the switch is between track and double, which only changes what the finish lays; it bumps `worldVersion` because a cancel can drop a fresh start junction). The keyboard shortcuts set the same flags, so toolbar and keys always agree. Town and Delete are full tools so everything works with a plain left click; Shift+click and right-click remain shortcuts for them under the track tools. Commands — `undo()`, `startSimulation()`, `stopSimulation()`, `toggleReservations()` — mirror U, Space, Esc, V (and `resetGame()` R; the toolbar asks for confirmation first). `Toolbar` renders the tool buttons (pressed = active), the commands (Run becomes Stop while running; Run is highlighted once `readyToStart()`), and money, each button labelled with its shortcut; it re-renders on a signature change, delegates clicks on `data-tool`/`data-command`, and blurs buttons after use. `Game.hintText()` is a short tip for the active tool (a rejected track finish leads with the reason) shown under the toolbar with the status line; train text lives in the orders panel (selected-train key hints in its footer, loads on the running cards). Disabled buttons are dimmed by colour, not `opacity` — translucent buttons became compositing groups that Chrome painted with stale neighbouring content.

**Input is plain event objects** — `{type: 'motion', pos}`, `{type: 'mouse', button: 'left'|'right', shift, pos}`, `{type: 'key', code}` (a `KeyboardEvent.code`) — so the browser and the tests drive the same `Game.handleInput`. `main.js` raycasts the pointer onto the ground plane to get `pos`, and keeps the camera keys (arrows, Q/E) and middle-button drags to itself.

**Towns are not part of the track graph.** A town is a catchment circle that accumulates passengers. Building a station (on a track inside the town's radius) is what connects it to the railway: the hit segment is split into approach tracks and a platform segment with entry/exit junction nodes.

**Game states:** `EDITING` (place towns, draw tracks, build stations, configure the train roster) → `SIMULATING` (trains run, money accumulates). `Escape` while simulating stops the run and returns to editing with the world intact (`_stopSimulation`): trains despawn, reservations release, and the per-run fleet cost (`fleetCostPaid`) is refunded, so stop → tweak signals → restart is money-neutral while fares earned are kept. `R` is the destructive full reset.

### Key systems

**Track drawing** (`game.js`, `track_editor.js`): Click a junction or empty ground to start a track (empty ground creates a fresh junction), click empty space to add curve waypoints, click a junction or track to finish. Creating a segment automatically creates its reverse. `TrackSegment` wraps a `Curve2D` and exposes `positionAt(t)`, `angleAt(t)`, and `length()`. Tracks are validated for curve radius and turnout angle at both ends. A finish click on a track splits it into a junction (`finishOnTrack`) — including the segment the drawing departed from, which is how a passing loop rejoins its own line as a pair of 3-way junctions. Waypoint-vs-join disambiguation is by distance from the start node (`hitTooCloseToStart`): a short sliver zone (`MIN_JOIN_DISTANCE`) on any track, a long one (`DEPARTURE_JOIN_DISTANCE`) on segments touching the start node, because the turnout limit forces departing loops to hug their line at first. A rejoin whose curve never swings `MIN_LOOP_OFFSET` clear of the segment it left is rejected (it would bury an identical-looking track under the original). Parallel tracks between the same two junctions are legal, so hit-testing (`findTrackAt`) and rendering (`Renderer._physicalTracks`) deduplicate the two directions of a physical track by reverse-twin identity, never by endpoint positions.

**Stations** (`TrackEditor.placeStation`): Press `P`, click a track inside a town's circle. Validates: town has no station yet, segment ≥ `PLATFORM_LENGTH + 20`, platform span gentle enough, not already a platform, not a double-track taper. Span ends snap to existing endpoints when close (5% of length or `HIT_RADIUS`). Placement is split into `_planPlatform` (validate, mutate nothing) and `_buildPlatform`. **On double track** — `findParallelTrack` finds another physical track parallel (within `PARALLEL_ANGLE`) at `DOUBLE_SPACING` (±`PARALLEL_TOLERANCE`) to either side — the station gets a platform on each track, side platforms facing outward; both are planned before either is built, so a station is never half-built. A lone platform faces the town. Platform segments are protected — no splitting (junctions) and no deletion while the station exists; removing the town removes the station (all its platforms).

**Train movement** (`train.js`): Advances `segmentProgress` (0–1) along the current `TrackSegment`. Capacity is 20 passengers per car, speed is 150 px/sec. While `dwellRemaining > 0` the train is stopped at a station and `move()` only counts the timer down.

**Track reservations — OpenTTD-style path signals** (`train.js`, `track_segment.js`): `TrackSegment.reservedBy` marks the train holding a segment; a segment is blocked for a train if it, *its reverse twin*, or a track it meets at a **flat crossing** is held by another train (head-on exclusion on the same physical track, plus diamond exclusion — see Flat crossings). A train reserves a **path**: `Train.tryExtendReservation()` collects route segments from `limitIndex + 1` through the next *safe waiting point* — the first segment with `exitSignal` for its direction, or the end of the route (the destination platform) — and `tryReserve`s the slice atomically (all-or-nothing; `limitIndex` unchanged on failure). The head may not advance past `route[limitIndex]`; at the boundary it re-attempts the extension and on failure halts with `waitingForTrack` set (retried every `move()`), recording the holder in `blockedBy` (the wait-for graph edge). Segments release when the **tail** clears them (the `_trimHistory()` hook) and on `setRoute()`; after a stop, `Game` re-reserves the segment the consist sits on, then extends. At simulation start every train's footprint is seeded **before** anyone extends (extending earlier would claim paths through unspawned trains).

**Path signals** (`track_editor.js`, `game.js`): `S` enters signal mode; clicking a track calls `placeOrCycleSignal` — it splits the segment (`splitTrackAtHit`) and sets `exitSignal` on both directed segments arriving at the new junction (a two-way signal). Clicking an existing signal junction cycles two-way → loose one-way → other loose one-way → strict one-way → other strict one-way → removed (`SignalState`, `_applySignalState`); junctions with ≠2 incoming plain segments are rejected (no signals on real junctions or platforms — the platform is its own safe waiting point). One-way signals additionally affect *routing* against their direction, and `TrackSegment.looseOneWay` picks how: **strict** (the default for a bare `exitSignal`) bars it outright, **loose** merely penalizes it (see Routing). The two flags always travel together via `TrackSegment.copySignalFrom` — splits, station placement, and `GameSnapshot` all use it, so a loose one-way can never be resurrected as a strict one. Rendering: a mast with a lamp on the right-hand side of the direction served, red by default, green while a reservation passes *through* it; a strict one-way adds a dark red no-entry bar on the far side of the track (a loose one leaves that side clear, since traffic may still come through it).

**Loose vs strict one-way signals**: the difference that matters is the *waiting point*, not the routing rule. `exitSignal` is per direction, so a one-way signal is a place where trains going the signalled way may stand and trains coming the other way may not — the latter must reserve straight through to their next stopping place. On a shared single-track approach to a junction that is exactly what stops a train from halting *past* the junction and fouling it: it holds back at the previous signal instead (e.g. on its branch). Strict one-ways cannot be used there because the line has to carry both directions; loose ones can. Strict remains the right tool for genuinely directional track (passing-loop branches), where barring the wrong way is the point.

**Double track** (`track_editor.js`): `D` toggles `TrackEditor.doubleTrack` (also mid-drawing; a mode, not an undo step), and every finish — at a junction, at a new junction (shift), or onto a track — then lays a **double section** between the start and end nodes instead of a single track (`_layTrack`; validation goes through `candidateTracks`/`_validateCandidates`, which check curvature, turnout at both ends, and crossings for each track, and reject centrelines shorter than `DOUBLE_MIN_LENGTH` with reason `"double_short"`). `planDoubleTrack` samples the drawn centreline every `DOUBLE_SAMPLE_STEP` and offsets two tracks `DOUBLE_SPACING`/2 to each side, easing to zero over a smoothstep taper (`doubleOffset`, a third of the section clamped to `DOUBLE_TAPER_MIN..MAX`) so both converge onto the end nodes in line with the centreline. Structurally a section is therefore a long passing loop between two ordinary junctions — routing, reservations, and turnout validation need nothing special, and sections chain at shared "pinch" junctions. `createDoubleTrack` builds each track as a chain of pieces split at the taper ends and every ~`DOUBLE_SIGNAL_SPACING` (pieces stay long enough for a platform). **Right-hand running**: the `right` track (relative to start→end) carries start→end traffic and the `left` one the reverse; each split carries a **strict one-way signal** serving its track's direction, so routing keeps every train on its own running line and following trains close up signal by signal. The **taper** pieces at each end (`TrackSegment.taper`) are paired with a `CrossingKind.FOUL` crossing: where the tracks converge, trains on both would overlap, so only one train may hold either taper — this also keeps opposing movements apart at a pinch. FOUL crossings are never drawn and are cloned with their kind by `GameSnapshot`; because splitting a segment drops its crossings, tapers are protected from splits, junctions, signals, and stations (`_splitBlocker`). Consequence of directional running without crossovers: **a train cannot turn back at a station on double track** — it can only reverse at stops on two-way track (e.g. single-track termini beyond the section), and loop validation rejects orders that would need to (see Routing) — unless a crossover provides the way back.

**Crossovers — scissors** (`track_editor.js`): the Crossover tool (`C`) lays a **scissors crossover** with a click on either track of a double section's parallel run (`planCrossover` → `placeCrossover`; the same plan drives the green ghost preview). Each line is split at an entry and an exit junction `CROSSOVER_LENGTH` apart, and two smoothstep S-bend diagonals (`crossover` + `taper` flags) join them, crossing at a real **diamond** that `TrackNetwork` detects like any flat crossing. "Right-hand", "entry" and "exit" are relative to each line's running direction, found geometrically by `_runningDirection` (right-hand running puts the other track on the left). The **trailing** diagonal (left line's exit → right line's exit) can never be taken by through traffic (it bends backwards through the junction); it carries trains that reversed at a stop beyond the scissors and run back to it, onto the other line in its own direction. The **facing** diagonal (right line's entry → left line's entry) carries trains forward onto the other line, wrong-way, to a platform just beyond, where they reverse and leave correctly — so a terminating train can use either platform. **Interlocking**: each line's middle piece (entry → exit) is a taper paired by FOUL crossings with both diagonals (straight-through trains on the two lines still pass each other; no diagonal move overlaps either); the piece arriving at each line's entry carries the **protecting signal**, a *loose* one-way (a strict one would bar the wrong-way move out of the entry junction after the facing diagonal; loose prices it, so a train crosses over only when the platform straight ahead is worse — e.g. occupied). **Deadlock avoidance**: the scissors must have `CROSSOVER_CLEARANCE` (a platform length + 10 — consists always fit a platform) of plain line beyond each end before any taper (`_clearAround`), and running signals within that distance past each exit are removed, so a train waiting either side never stands in the scissors or a neighbouring interlocked area (waiting in one for the other deadlocked two trains). `_clearTurnbackSignals` then clears the **wrong-way stretches** to the nearest platform beyond each end: downstream from each exit (trailing moves), and upstream from each entry keeping the protecting signal (facing moves) — strict one-ways there would bar the moves, and a train waiting at one would deadlock against the wrong-way train. Section-end signals are never touched. A station placed later on double track runs the same walks from its side (`_linkTurnbacks`). Clicks slide up to `CROSSOVER_NUDGE` to the nearest spot where all four junctions land on one plain piece per line, clear (`NODE_CLEARANCE`) of nodes; otherwise the reason is reported. One undo step. With platform choice now real, dispatch, the lookahead, and `planLoop` only target **viable** platforms (`TrackNetwork.viablePlatforms`: those from which the next stop is reachable) — otherwise the cheapest platform could be one the train cannot leave in the right direction.

**Flat crossings — diamonds** (`track_crossing.js`, `track_network.js`, `track_segment.js`): two tracks that cross in space without connecting (`CrossingKind.DIAMOND`; the same `TrackCrossing` mechanism carries double-track `FOUL` pairs). A crossing adds **no connectivity** — it is deliberately *not* a `NetworkNode` (that would let trains turn at the diamond, invite signals and splits onto it, and fail turnout validation). It is purely a mutual-exclusion relation, and it carries no `reservedBy` of its own: whether a diamond is locked is derived from the two tracks' existing reservations, so release, `_trimHistory`, and turnaround logic are untouched. `Train.blockingTrain()` walks `seg.crossings` after the segment and its twin, and everything downstream (`isBlocked`, `tryReserve`, `routeCost`, Dijkstra relaxation, the `blockedBy` wait-for graph) inherits diamond exclusion from that one place — including routing *around* an occupied diamond via `BLOCKED_PENALTY`. Each crossing is registered on all four directed segments of the two tracks so lookup from any direction is one array walk. Detection is geometric and automatic in `TrackNetwork.addSegment` — the chokepoint every structural edit passes through, so crossings cannot drift from the geometry; `GameSnapshot` opts out (`detectCrossings = false`) and clones the known set through its `segmentMap` instead, since re-detecting per segment would make undo capture quadratic. Pairs sharing a node are exempt (`sharesNode`), and intersections within `CROSSING_NODE_CLEARANCE` of an endpoint are discarded — together these are what let a crossover arm terminate on the track it joins without registering a spurious diamond, so a scissors yields exactly one crossing (arm against arm) while trains running straight through on either main line are unaffected. Exclusion is at segment granularity, not the diamond itself: holding any part of a long line locks the whole crossing track. That matches the granularity path signalling already gives, and the player's lever is the same — a signal near the diamond splits the segment and tightens the block. The editor rejects crossings shallower than `MIN_CROSSING_ANGLE` (12°, reason `"crossing"`) and any crossing over a platform (`"crossing_platform"`), and `placeStation` refuses a platform span containing an existing diamond. Rendered as a hollow grey lozenge — deliberately unlike a junction's solid white diamond — tinted in the holder's colour under the `V` overlay (FOUL pairs are skipped).

**Deadlock detection** (`game.js`): once per second (`DEADLOCK_CHECK_INTERVAL`), walk the wait-for graph (`Train.blockedBy`) from each blocked train — a revisit on the walk is a cycle ⇒ deadlock; as a net, all trains simultaneously blocked for > `ALL_BLOCKED_TIMEOUT` (10 s) counts too. Deadlocked trains get a red ring and a status message; the simulation keeps running (the player resolves it with `Escape` — stop, fix the signals, restart — or wipes with `R`). A queue behind a moving or dwelling leader is *not* flagged.

**Multiple trains** (`game.js`, `train_plan.js`): The edit-mode roster is an array of `TrainPlan` (orders + car count each); `T` buys a train, `X` sells, `,`/`.` switch the selected train, and `O`/`[ ]` edit the selected plan (`Game.trainOrders`/`Game.carCount` are accessors forwarding to it). Simulation start validates every plan's loop, requires **distinct first stops** (each train spawns parked at its first stop's platform), and charges `fleetCost()` — `TRAIN_COST` (500) per extra train plus `COST_PER_CAR` (150) per extra car. Each train is drawn in its `TRAIN_COLORS` hue (head car, order badges, order-loop preview, HUD swatch, panel card).

**Orders** (`game.js`, `orders_panel.js`): an order list is a loop of towns, and **a station may appear several times** (A → B → C → B); `Train.currentOrderIndex` walks the list, so repeats need nothing special in dispatch. The only rule is that a stop may not directly repeat the one before it — a train cannot route from a platform to itself — and the loop wraps, so the last stop may not equal the first either (A → B → A is invalid; A → B is the shuttle). `Game.orderProblem(plan)` is the single statement of that rule (plus "at least 2 stops" and "every stop has a station"): `_startSimulation` refuses with it, and the panel shows it as a warning. All order edits go through `Game`'s API — `addOrder(train, town)` (refuses a repeat of the current last stop up front), `removeOrder`, `moveOrder(train, index, ±1)`, `clearOrders`, `setCarCount`, `selectTrain`, `_buyTrain`, `_sellTrain(index)` — each one undo step, rejected edits burning none, all no-ops while simulating. Map clicks in orders mode (`O`, or the panel's *Pick on map*) **append** the clicked town, including one already in the list; removal is right-click (last stop) or the panel. Removing a town drops every visit to it and collapses stops left back to back (`TrackEditor.removeTown`). Towns get names on placement (`TOWN_NAMES`/`townName`, keyed by `nextColorIndex`, so undo reuses them); `GameSnapshot` clones repeated stops onto the same cloned town. **Orders panel** (`OrdersPanel`, the `#orders` aside in `index.html`): one card per roster train — cars ±, the stop list with ↑/↓/× per row, an *Add stop…* dropdown of stationed towns, *Pick on map*, *Clear*, *Sell*, the plan's `orderProblem` warning — and *Buy train*; while simulating the cards go read-only and show load, status, and the stop each train is at (`here`) or heading to (`next`). It re-renders only when a signature of what it shows changes, handles clicks by delegation on `data-action`, and blurs its controls after use so Space and the letter keys stay with the game (`main.js` also leaves keys alone while a dropdown is focused). On the map, order badges are grouped per station per train, listing every visit's number (`2 · 4`).

**Routing** (`track_network.js`): Dijkstra over the directed graph; `findRoute(from, to, forTrain = null, arriving = null, exitSeg = null, allowReversal = false)` returns an array of `TrackSegment`. **The search is direction-aware — no switchbacks**: its state is the directed segment a path arrives on (visited is keyed per segment, not per node), and a junction transition is only legal when `canContinue(prev, next)` holds — `next` is not `prev`'s reverse twin and the departure heading stays within `MAX_THROUGH_ANGLE` (90°) of the arrival heading, so a train never bends backward through a junction the way no real turnout allows. Reversal is permitted only as the *first* hop with `allowReversal` (a train standing at a station stop departing back along its own segment — how dead-end termini turn around); `arriving` seeds the heading at `from`, and `exitSeg` makes the goal count only when the path can continue onto it (used so the platform traversal appended by `findRouteToPlatform` is always physically takeable). Dispatch (`Game._dispatchToNextOrder`) passes the platform segment the train stands on with `allowReversal = true`; the mid-route re-path (`Train._repathProvisionalTail`) passes `route[limitIndex]` without reversal. **One-way signals oppose routing against them**: `oneWayAgainst(seg)` returns `OneWay.NONE`/`LOOSE`/`STRICT` for a directed segment whose start junction hosts a signal serving only the opposite direction (the segment's twin arriving there carries `exitSignal`, no other arriving segment does, and `looseOneWay` on that twin picks loose vs strict). `STRICT` skips the segment outright — this is what makes directional passing-loop branches work, forcing opposing trains onto different branches to pass inside the loop. `LOOSE` instead adds `ONE_WAY_PENALTY` (2 000) to the relaxation, so the direction is taken only when nothing better exists. The penalty sits *below* `BLOCKED_PENALTY` deliberately: running the wrong way past a loose signal is safe (reservations still keep trains apart), so a train prefers it to queueing behind occupied track — strict is the lever when that is not wanted. `routeCost` mirrors both penalties, since the lookahead compares its output against `findRoute`'s. **Stations with several platforms** (double track): `findRouteToStation(from, platforms, …)` returns the cheapest `{ route, platform }` over `findRouteToPlatform` for each platform (by `routeCost`, so traffic-aware with `forTrain`); dispatch and the lookahead target all of the next station's platforms (`Train.targetPlatforms`; `targetPlatform` is a single-platform accessor). **Loop validation** (`planLoop(stops)`, each stop a station's platform array; `firstUnroutableStop` wraps it) walks the loop as dispatch will — each leg's `arriving` platform traversal, `allowReversal = true`, the greedy cheapest platform — trying each of the first stop's platforms as the start, and returns the one that works as the train's spawn platform. Because the greedy choice can end a lap on a different platform of the first stop (out on the eastbound platform, back on the westbound one), laps are walked until one starts from an already-used platform; this is what rejects, at start, orders that would need a train to turn back on one-way double track. It inherits both one-way rules, so mis-signalled layouts and order loops needing a mid-route switchback (e.g. two stations on branches fanning the same way off one junction) are rejected at simulation start — but it stays reservation-blind (always called without `forTrain`), so layouts are never rejected because of where trains happen to stand. Dispatch uses `findRouteToPlatform(from, platform, forTrain)`, which enters at the cheaper platform end and always finishes by traversing the platform segment.

**Adaptive routing — per-signal lookahead** (`track_network.js`, `train.js`): with `forTrain` given, a segment unavailable to that train (`Train.isBlocked` — held by another train directly or via the reverse twin) costs `BLOCKED_PENALTY` (10 000) extra: traffic is a *penalty* to route around, never a reason to fail, and with no free alternative the shortest route is still returned. The train's own reservations cost nothing; `oneWayAgainst` stays layout rather than traffic — a hard skip when strict, a fixed `ONE_WAY_PENALTY` when loose, neither of which depends on who is where. Both dispatch sites pass the train (and set `Train.network`/`Train.targetPlatform`), so the initial branch and platform-entry-end choices avoid parked traffic. The payoff is `Train._repathProvisionalTail`, run inside **every** `tryExtendReservation` before the slice is reserved: the provisional tail beyond `limitIndex` is re-pathed from `route[limitIndex].nodeEnd` to `targetPlatform` with penalties, and a better tail is spliced onto the kept prefix — history, indices, and held reservations intact (the discarded tail lies beyond `limitIndex`, so it held nothing) — then `stopProgress` is recomputed via `Train.stopPointOn` (the new tail may enter the destination platform from the other end). Hysteresis: a *blocked* tail is abandoned for any strictly cheaper one, a *free* tail only for one cheaper by `SWITCH_MARGIN` (`CAR_LENGTH`×10), so near-equal branches never flip-flop (`network.routeCost` does the comparing). Because the re-path runs while the train is still rolling toward the boundary, a train facing a blocked loop branch diverts onto the free one **at speed**, and convoy followers spread across parallel branches; a blocked train's per-frame reservation retries re-path on a throttle (`Train.blockedTime` ≥ `REROUTE_RETRY_INTERVAL`, 1 s; `_wasWaiting` distinguishes a fresh boundary from a blocked retry). Skipped while the train is still anchored at its departure platform (`limitIndex == -1`, before the first extension): the turnaround/roll-through anchoring came from the route's first segment and would not survive a tail swap, and dispatch was already traffic-aware. There is deliberately no `getOutgoing(node).length < 2` early-out: outgoing counts the reverse twin (only dead ends have < 2), and a train waiting at an approach signal diverges further on, so skipping there would break exactly the passing-loop case. This is what makes passing loops work with plain **two-way** signals. The re-path happens inside `move()` and thus before deadlock detection each tick, and a fruitless re-path leaves `blockedBy` in place, so genuine deadlocks still flag. The train halts at the middle of the platform (`Train.stopProgress`, set via `stopPointOn` on dispatch): `Game._arriveAtPlatform()` unloads/boards and starts a 2 s dwell (`Train.dwellTime`); when it expires `Game._departFromStop()` dispatches the next order from the platform's exit node and re-anchors the train via `Train.resumeFromStop()` — if the new route leaves along the platform's reverse segment (a dead-end station) the train turns around in place, otherwise the platform segment is prepended so the train rolls forward through its remainder onto the new route (`Train.boardedThisLeg` marks the stop as done for the leg).

**Undo** (`game_snapshot.js`, `game.js`): every build action calls `_pushUndo()` first (a deep `GameSnapshot.capture` of towns, network, roster) and `_discardUndo()` if the action then fails, so rejected clicks never burn an undo. `U` pops and restores (`UNDO_LIMIT` 50). A fresh free-draw start junction is captured without itself (`_pushUndoForFinish`), so undoing a finished track removes it too.

**Passenger economy** (`game.js`): Towns generate 0–0.5 passengers every 10 frames whether or not they have a station. Delivering passengers earns `10 × passenger_count`. Starting money: 1000; the fleet cost (extra trains and cars) is deducted at simulation start. Only towns with stations can be train order stops.

**Rendering** (`renderer.js`): game pixels map onto the ground plane as `(x, 0, y)` — one pixel is one world unit, and the default camera looks north (-z) at the original 1152×648 play area. The scene has three layers: **static** (towns with houses kept clear of the track, ballast/sleepers/rails, platforms with shelters, junction diamonds, crossing lozenges, signal masts) rebuilt whenever `Game.worldVersion` changes — `Game` bumps it on every non-motion input, undo, reset, and simulation stop, so any new mutation path must bump it too; **trains**, pooled meshes re-posed each frame from `Train.pointBehind`; and **overlay** (drawing preview coloured by curvature, waypoints, hover rings, order-loop previews, deadlock rings) rebuilt every frame, plus the `V` reservation tint rebuilt when the reservation set changes. Signal lamps and crossing tints are recoloured per frame. Text (order badges, "Waiting: N", train loads, "Boarding..."/"Waiting for path...", turnout-angle readouts) is drawn on a 2D canvas over the WebGL one at projected positions; the toolbar, tip line, status message, and orders panel are DOM elements in `index.html` (see Tools and the toolbar, Orders). Tool feedback on the map: a ghost catchment under the cursor with the Town tool, the track (red; amber for a protected platform) or town the Delete tool would remove, junction hover rings only for the track and signal tools.

**Tests** (`tests/`): a tiny harness (`test_base.js`: `suite`, `t`, `eq`, `approx`, `gt`, `isTrue`, `isFalse`) and one file per module; simulation tests drive a real `Game` with `process(1 / 60)` ticks. `window.railway` exposes `{ game, view }` in the browser for console debugging and automated checks.

### Input (editing mode)

| Action | Effect |
|---|---|
| Toolbar (top left) | Pick a tool — Track, Double, Town, Station, Signal, Crossover, Delete — or Undo, Run/Stop, Paths (reservation overlay), Reset; each button shows its shortcut |
| Shift+Left-click empty | Place town (or the Town tool: plain click) |
| Left-click junction/track/empty | Start track (empty ground creates a junction) |
| Left-click empty (while drawing) | Add waypoint |
| Shift+Left-click (while drawing) | Finish at new junction and continue drawing |
| C | Crossover tool: click double track to add a scissors crossover (trains can turn back at stations either side, and use either platform) |
| D | Toggle double-track drawing (also while drawing): finishes lay a right-hand-running double section with one-way signals |
| Right-click / Escape | Cancel drawing |
| Right-click track / town | Delete track / remove town and its station (or the Delete tool: plain click) |
| Z | Undo last waypoint (of the in-progress track only) |
| U | Undo the last build action — town, track, split, station, delete, order edit (LIFO snapshots; works in the orders/station sub-modes, ignored while drawing) |
| P | Place a station (click a track inside a town circle) |
| S | Place signals (click a track to place a two-way signal; click a signal to cycle two-way → loose one-way ↔ → strict one-way ↔ → removed) |
| V | Toggle the reservation overlay (any phase; drawn while simulating) |
| O | Edit the selected train's orders (click towns with stations to append them; repeats allowed; right-click removes the last stop) |
| T | Buy a train (added to the roster and selected; undoable) |
| X | Sell the selected train (the roster never goes empty; undoable) |
| , / . | Select the previous / next roster train (also in orders mode) |
| [ / ] | Remove / add a car on the selected train |
| Orders panel (top right) | Per-train cards: cars, reorder/remove/add/clear stops, pick stops on the map, buy/sell trains; footer lists the keys for the selected train |
| Escape (in a tool) | Put the tool down, back to drawing track |
| R | Reset the game to the initial empty editing state (works in any phase) |
| Space | Start simulation |
| Escape (while simulating) | Stop the run and return to editing — world, roster, and earnings kept; fleet cost refunded |

### Camera (any phase)

| Action | Effect |
|---|---|
| Mouse wheel | Zoom toward the cursor |
| Middle-drag | Pan (the grabbed ground point follows the cursor) |
| Shift+Middle-drag | Orbit (yaw and pitch) |
| Arrow keys | Pan |
| Q / E | Rotate |
